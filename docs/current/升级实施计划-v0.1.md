# 个人工作台升级实施计划（v0.1）

> 文档性质：后续迭代的执行路线图与验收基线  
> 日期：2026-08-13  
> 适用版本：当前 `0.1.0` 本地优先 MVP  
> 当前执行依据：本目录中的文档。历史文档已归档，不作为后续实现依据。

---

## 一、现状与升级目标

### 1.1 当前基线

当前项目已具备个人工作台的主要业务模块：任务、日程、项目、目标、习惯、周期计划、复盘、收件箱、知识库、标签、全局搜索和 AI 复盘草稿。

现有工程基础：

- 桌面端：Tauri 2 + Rust
- 前端：React 19 + TypeScript + Vite + Tailwind CSS
- 数据：SQLite，前端通过 Repository 层访问，TanStack Query 管理缓存
- 测试：Vitest 单元/组件测试；当前基线为 20 个测试文件、183 个测试通过
- 路由：仪表盘及 11 个业务页面已接入
- 构建：前端生产构建通过；Tauri 可生成调试可执行文件，Windows 安装包打包尚未完成验证

### 1.2 本轮升级的总目标

将当前“功能可演示的 MVP”升级为“可长期自用、数据可信、可安装验证的单机发布版”。

优先保证以下四件事：

1. 数据不会因升级、误操作或设备问题而难以恢复。
2. 核心工作流可以持续使用，并且失败时有明确反馈。
3. 已承诺的关键能力形成闭环，而不是只有表结构或局部 UI。
4. 可以在干净 Windows 环境中安装、启动、升级和验证。

### 1.3 本轮暂不做的事项

在以下能力进入稳定状态前，不启动大规模开发：

- 多设备实时同步、冲突合并与协作
- 移动端正式发布
- 富文本编辑器替换、复杂知识图谱
- 大规模视觉重构或新增大量独立模块
- 面向陌生用户的账号体系、云端服务和商业化

原因：这些工作会显著扩大数据一致性、权限、安全和维护成本，不能替代单机版的可靠性建设。

## 二、执行原则

### 2.1 优先级规则

按以下顺序安排需求：

1. 数据安全、数据正确性、升级兼容性
2. 每日高频流程：记录、安排、完成、复盘、检索
3. 关键关联闭环：任务—项目—目标、收件箱—知识库—复盘
4. 性能、可观测性、代码规范和发布自动化
5. 同步、移动端与高级智能能力

### 2.2 每个功能的完成定义（Definition of Done）

一个需求只有同时满足以下条件才算完成：

- 有明确的用户场景、输入、输出和异常行为。
- 数据库变更通过新增迁移实现，不修改已经发布的迁移语义。
- Repository 与 Hook 的缓存失效范围正确；相关页面刷新后数据保持一致。
- 至少覆盖关键成功路径与一个失败/边界路径的自动化测试。
- 有加载、空状态、保存失败或不可用状态的用户反馈。
- 手动在 Tauri 桌面端验证一次；涉及升级或数据时需在旧数据上验证。
- 更新本计划中的状态、验收记录及必要文档。

### 2.3 建议的迭代节奏

以 1 周为一个小迭代、2 周为一个可验收里程碑：

- 开始前：只选择 1 个主目标和不超过 3 个可交付事项。
- 开发中：先改数据层与测试，再接 Hook 和页面交互。
- 结束前：跑类型检查、全量测试、前端构建和桌面端手动验证。
- 结束后：记录已知问题，不把未完成能力标为完成。

## 三、路线总览

| 阶段 | 目标 | 主要产出 | 建议优先级 |
|---|---|---|---|
| R0 | 可靠单机版与发布基线 | 迁移规范、备份恢复、错误反馈、Windows 安装验证 | 必须先做 |
| R1 | 核心工作流闭环 | 搜索升级、标签切片、知识双链、复盘与计划联动 | 高 |
| R2 | 工程化与安全收口 | 权限收敛、密钥安全、性能优化、自动验证 | 高 |
| R3 | 同步前准备 | 变更日志、冲突策略、导入导出稳定格式 | 中，R0-R2 完成后 |
| R4 | 多端同步与扩展 | 同步服务、设备管理、移动端评估 | 后置 |

建议的实际执行顺序：先完成 R0，再以 R1 中“搜索/知识闭环”为主线推进，同时穿插 R2 的低风险工程项。R3、R4 仅保留设计和调研，不提前实现。

## 四、R0：可靠单机版与发布基线

### R0.1 建立数据库迁移规范

#### 目标

确保应用升级时可以安全地从旧数据结构迁移到新结构，避免直接修改初始建表脚本造成新旧用户行为不一致。

#### 实施事项

1. 约定迁移命名：`002_<功能名称>.sql`、`003_<功能名称>.sql`。
2. 在 Rust 端按版本顺序注册迁移；已发布迁移仅允许补充注释，不允许改写业务语义。
3. 为每次迁移写明：前置版本、变更内容、数据回填方式、回滚/恢复方案和验证 SQL。
4. 新增一个“迁移验证”测试约定：至少验证全新数据库与从上一版本升级的数据库都可启动。
5. 在设置页或诊断信息中显示应用版本、数据库迁移版本和数据库位置（不展示敏感配置）。

#### 验收标准

- 新增一次示例迁移并在空数据库、已有数据数据库上分别成功执行。
- 旧数据在升级后可正常查询、编辑、删除和重启读取。
- 迁移失败时不允许静默继续启动；用户能看到恢复指引。

#### 注意事项

- 当前 `001_initial.sql` 是版本 1 的唯一基线；后续字段、索引、触发器均新增迁移。
- 涉及大量数据重写时，优先“加新列 → 回填 → 切换读取 → 后续版本清理旧列”，避免一次性破坏性修改。

### R0.2 备份、导出、导入与恢复

#### 目标

让用户在升级、误删或换设备前能够主动保存数据，并在恢复前清楚知道会发生什么。

#### 第一版范围

- 导出完整业务数据为带版本号的 JSON 备份文件。
- 导入前先校验格式、应用版本和数据关系。
- 恢复采用“全量恢复”语义：先自动创建当前数据备份，再经用户二次确认覆盖业务数据。
- API Key、桌面配置、日志不进入业务备份；附件文件需明确是否包含。
- 在设置页提供：立即备份、从备份恢复、查看最近一次备份时间、导出失败提示。

#### 备份格式建议

```json
{
  "format": "luluKing-backup",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "databaseVersion": 1,
  "exportedAt": "2026-08-13T00:00:00.000Z",
  "data": {
    "tasks": [],
    "projects": [],
    "...": []
  }
}
```

第一版使用 JSON 的原因是格式可审阅、可版本化、便于在未来导入迁移。若前端 SQL 调用无法保证恢复过程的原子性，则把“导入校验与写入事务”下沉到 Rust 命令，不采用尽力而为的多次前端写入。

#### 实施事项

1. 明确备份表清单和导入顺序，先父表后关联表。
2. 增加备份格式校验：必填字段、版本、ID 唯一性、外键引用、枚举状态和日期格式。
3. 先实现只读“备份预览”，展示实体数量、导出时间和版本，不直接写库。
4. 实现恢复前自动备份、二次确认和成功后的应用重启/数据刷新。（已完成：预览、自动安全备份、Rust 事务恢复与重新加载；附件记录存在时安全拒绝）
5. 为空数据、完整数据、损坏文件、跨版本文件、包含孤儿引用的文件增加测试。
6. 明确附件策略：第一版若文件附件尚未在 UI 使用，则在界面和文档中声明“不含附件”；启用附件后再升级为数据包格式。

#### 验收标准

- 导出后重新导入到空环境，任务、关联、标签、笔记、复盘等数据数量和关键关系一致。
- 导入损坏或不兼容文件不会写入任何业务数据。
- 覆盖恢复前自动生成可用备份；恢复后重启应用仍可正常使用。
- 导出的文件不包含 AI Key。

### R0.3 核心异常处理与状态反馈

#### 目标

让数据库、AI、文件和导入失败时可理解、可恢复，而不是仅出现在开发者控制台。

#### 实施事项

- 已完成：建立统一的页面级错误提示与操作级提示（保存中、成功、失败、重试）。
- 已完成：为 Query 错误提供统一显示策略，避免任务页和仪表盘默默呈现为空列表。
- 已完成：给 AI 调用增加配置缺失、网络失败、取消和服务端错误的中文提示；不再展示原始服务端响应体。
- 已完成：任务、复盘等关键写操作仅在成功后关闭弹窗，失败时保留表单内容。
- 已完成：任务删除、批量删除、复盘删除及 AI 草稿覆盖改为应用内二次确认；恢复流程保持原有确认。

#### 验收标准

- 模拟数据库失败、网络失败时，页面显示明确状态且不丢失用户输入。
- 常规操作不再依赖浏览器默认弹窗作为唯一交互反馈。

### R0.4 Windows 打包与安装验证

#### 目标

获得可安装、可启动、可保留数据升级的 Windows 发布流程。

#### 实施事项

1. 固定 Windows 打包所需工具及其离线/代理安装方式，解决 Wix 依赖下载受网络和权限影响的问题。
2. 在干净 Windows 用户环境验证 MSI：安装、启动、创建数据、卸载、升级安装。
3. 明确数据库和附件所在目录；卸载时默认保留用户数据，删除数据必须显式选择。
4. 增加版本号升级检查和发布说明模板。

#### 验收标准

- 可以在无开发环境的 Windows 机器上安装并启动。
- 从上一版本升级后，数据库迁移和原有数据正常。
- 记录安装包校验值、版本号和最小支持系统版本。

### R0 里程碑验收

- 用户可完成“记录任务 → 关联项目/目标 → 排入日程 → 复盘”的基本流程。
- 用户可导出、恢复自己的数据，并且恢复失败不会破坏现有数据。
- 生产构建、全量测试、类型检查通过；Windows 安装包完成一次干净环境验证。
- 已知限制在设置页或发布说明中明确列出。

## 五、R1：核心工作流闭环

### R1.1 搜索升级

#### 现状

当前搜索使用跨表 `LIKE` 查询，覆盖任务、笔记、项目、目标；不具备排序相关度、标签过滤、习惯/复盘/事件检索和搜索语法。

#### 目标

实现对个人数据“找得到、看得懂、能继续操作”的搜索体验。

#### 实施顺序

1. 做 FTS5 可用性验证：在实际 Tauri 打包环境确认 SQLite 是否支持 FTS5，而不只依赖开发环境判断。
2. 若可用，新增独立迁移建立 FTS 索引与同步策略；若不可用，保留 `LIKE` 降级方案，并增加普通索引和明确的搜索范围限制。
3. 扩展检索对象：任务、笔记、项目、目标、习惯、日程、复盘、标签。
4. 支持最小过滤语法：`type:任务`、`tag:性能`、`status:未完成`；无法解析的词按普通关键词搜索。
5. 搜索结果按类型分组、显示命中上下文，并支持直接跳转或完成任务。
6. 记录搜索性能基线：常见查询在数千条数据下应有可接受响应时间。

#### 验收标准

- 含关键词、标签、状态过滤的查询结果正确，不返回软删除数据。
- 搜索结果可以导航到实体所在页面并定位/打开编辑状态。
- FTS 不可用时，降级搜索仍然正确可用。

### R1.2 标签能力闭环

#### 目标

让标签真正成为跨任务、项目、目标、知识和复盘的横向切片，而不只出现在部分编辑框中。

#### 实施事项

- 补齐各实体的标签编辑入口，按照高频顺序接入任务、项目、目标、笔记、习惯、复盘、日程。
- 增加标签详情/切片页：查看一个标签下不同类型的实体，并可进一步筛选。
- 支持标签归档、改名、合并同义标签；合并必须在事务内完成引用迁移。
- 定义标签删除策略：默认不物理删除，有引用时提示改为归档或合并。

#### 验收标准

- 同一标签能关联至少四种实体，并在切片页正确展示。
- 合并标签后，所有历史关联仍可查询。
- 标签编辑不会产生重复名称或无限缓存刷新。

### R1.3 知识库与双向链接

#### 产品决策

第一版不引入富文本编辑器和图谱。以当前纯文本编辑为基础，仅支持 `[[笔记标题]]` 的精确双向链接，优先解决“关联可建立、可回看”。

#### 实施事项

1. 编辑笔记时解析 `[[标题]]`，提供已存在笔记的自动补全和未匹配提示。
2. 保存笔记时在事务内更新该笔记的链接记录，避免重复和失效关联。
3. 笔记详情显示“链接到”和“被哪些笔记链接”。
4. 支持笔记关联目标、项目、任务；先实现展示与跳转，再考虑图形化。
5. 定义重名笔记策略：优先让用户选择目标笔记，不能仅依标题模糊猜测。

#### 验收标准

- 新增、修改、删除链接文本后，正向与反向关系同步更新。
- 被删除或归档的目标不会导致笔记详情崩溃，能显示失效关联提示。
- 关联内容可通过搜索和实体详情进入。

### R1.4 周计划与复盘联动

#### 目标

落实“计划是承诺、复盘负责关闭循环”的业务设计。

#### 实施事项

- 周计划中可从待办池选择任务，并记录承诺关系或结构化任务列表。
- 周复盘自动汇总当期计划完成情况、逾期任务、收件箱待处理数、习惯完成情况。
- 未完成承诺必须提供“完成 / 推到下期 / 回到待办池 / 放弃”的显式动作。
- AI 草稿只作为可编辑建议，不能绕过用户确认修改业务数据。

#### 验收标准

- 周计划和复盘对同一时间范围的统计一致。
- 用户可以在复盘中完成未完成任务的去向决策。
- AI 不可用时，手工复盘流程仍完全可用。

### R1 里程碑验收

- 搜索、标签、知识链接和复盘能串成一条“记录—组织—检索—回顾”的闭环。
- 不依赖 AI 也能完成全部核心流程。
- 高价值关联有数据层测试和手动端到端测试。

## 六、R2：工程化、安全与性能收口

### R2.1 Tauri 权限与内容安全

#### 风险

当前 WebView CSP 为空，HTTP 权限允许广泛 HTTPS 访问，文件系统能力范围也较宽。AI 支持自定义兼容接口，因此需要在安全与灵活性之间明确取舍。

#### 实施事项

- 为生产环境配置最小可行 CSP，并在应用主要页面和 AI 调用场景中验证。
- 收窄文件系统权限到实际应用数据目录和用户明确选择的文件路径。
- 对 AI Base URL 强制使用安全协议；若允许本地模型，单独提供受控的本地地址策略。
- 在设置页显示当前 AI 服务地址、模型和连接测试结果，但绝不回显完整 Key。
- 评估将 API Key 从普通配置文件迁移至操作系统凭据存储或加密保险库的成本；迁移前后需兼容已有配置并支持删除旧 Key。

#### 验收标准

- 常规功能在收紧权限后仍能工作。
- 日志、备份、导出和界面均不会泄露 API Key。
- 设置 AI 服务失败时有清楚、无敏感信息的错误反馈。

### R2.2 性能与包体

#### 现状

当前前端生产主包约 506KB，构建已提示超过 500KB。

#### 实施事项

- 使用路由级懒加载拆分低频页面（设置、知识库、复盘、搜索等），保持首屏仪表盘和任务页优先加载。
- 检查图标、日期库和 UI 组件的实际引入量，避免全量引用。
- 为搜索和大列表增加输入防抖、分页/限制和必要的虚拟化评估。
- 记录优化前后构建产物大小与首屏可交互体验；只做有测量依据的优化。

#### 验收标准

- 主入口包显著低于当前基线，且页面切换无明显闪烁或错误。
- 数千条任务/笔记下，任务列表和搜索仍保持可用。

### R2.3 测试与交付流水线

#### 实施事项

- 将 `tsc --noEmit`、全量 Vitest、生产构建设为每次合并前的固定检查。
- 补充 Repository 集成测试或真实 SQLite 冒烟测试，覆盖迁移、备份恢复和关键关联。
- 补充页面级关键流程测试：新建任务、批量操作、收件箱升级、AI 配置缺失、恢复导入失败。
- 维护桌面端手动测试清单：首次启动、数据库迁移、安装升级、离线使用、备份恢复、AI 失败。
- 评估并在条件成熟时接入 Windows CI 打包；产物上传前应完成基础启动验证。

#### 验收标准

- 每个 R0/R1 新能力都在测试或手动清单中有对应覆盖。

## 八、建议的首个 2 周执行清单

### 第 1 周：数据安全骨架

1. 确认应用数据目录、数据库文件位置和附件当前实际使用情况。
2. 制定并实现迁移注册规范；新增一个无破坏性的 `002` 迁移作为流程验证。
3. 定义 JSON 备份格式、表清单、导入顺序和错误码。
4. 实现“导出备份 + 备份预览”，暂不开放覆盖恢复。
5. 补充备份序列化、格式校验和迁移启动测试。

本周验收：可以导出一份不含敏感配置、结构可验证的完整备份，并在测试中覆盖损坏文件。

### 第 2 周：安全恢复与发布冒烟

1. 实现全量恢复前自动备份、二次确认和失败回滚/原子性保障。
2. 在空数据与已有数据环境完成导出—恢复—重启验证。
3. 完善关键页面的加载/错误提示。
4. 固定 Windows 打包依赖，完成一次 MSI 安装、卸载、升级验证。
5. 写出首个发布说明和已知限制清单。

本周验收：即使恢复失败，用户现有数据仍可保留；安装包可在干净环境完成基本使用流程。

## 十、风险清单与决策门槛

| 风险 | 影响 | 处理原则 | 触发升级/暂停条件 |
|---|---|---|---|
| 迁移失败或误改历史迁移 | 用户无法启动或数据损坏 | 迁移不可改写、升级前备份、旧数据测试 | 出现一次不可恢复数据错误即暂停新增功能 |
| 导入非原子写入 | 产生半恢复数据 | 先预览校验，必要时下沉 Rust 事务 | 无法证明恢复原子性则不上线恢复入口 |
| AI Key 泄露 | 用户账户与费用风险 | 不写入日志/备份，迁移至安全存储 | 发现可读明文泄露路径立即修复 |
| 搜索数据增长变慢 | 核心体验下降 | 先基准测试，再决定 FTS/索引 | 常见查询明显卡顿时优先处理 |
| 过早做同步 | 冲突和维护成本失控 | 先稳定单机与备份 | R0-R2 未完成不得排期同步 |
| 打包依赖外部下载 | 无法稳定发布 | 固定工具链、准备离线方案 | 发布机无法重复构建时不发布 |
