## 一、目标与边界

本任务建立后续数据库变更的迁移规范，并交付第一版“只写入本地应用数据目录”的 JSON 备份能力。

本任务包含：

- 新增版本 `002` 的无破坏性迁移，用于验证迁移登记流程。
- 业务数据导出为可读、可版本化的 JSON 文件。
- 设置页支持立即备份、查看最近一次有效备份和导出失败提示。
- 备份文件基本格式校验，用于展示最近备份信息。

本任务不包含：

- 选择外部文件、导入、覆盖恢复或自动恢复。
- 附件文件打包与附件记录导出。
- AI 配置、API Key、日志、同步设备状态的导出。
- 面向多端同步的全局 ID 或冲突处理。

恢复入口必须在导入校验、原子写入和恢复前自动备份完成后才可开放。

## 二、数据库迁移规范

### 2.1 版本与命名

- 首次发布基线为 `001_initial.sql`，版本号为 `1`。
- 后续迁移使用 `NNN_<简短英文名称>.sql`，例如 `002_migration_baseline.sql`。
- Rust 端按版本升序显式注册每个迁移；当前应用数据库版本为 `4`。
- 已发布迁移不得修改业务语义。字段、索引、数据修复和触发器一律新增迁移。

### 2.2 每次迁移必须记录

- 前置数据库版本和目标版本。
- Schema、数据回填及索引变更。
- 对现有数据、备份格式和恢复流程的影响。
- 验证方式：空数据库启动、上一版本数据升级、重启后读写。
- 失败后的恢复方式；破坏性变更采用“新增 → 回填 → 切换 → 后续清理”。

### 2.3 本次 `002` 迁移

`002_migration_baseline.sql` 仅执行无副作用 SQL，用来确认从版本 `1` 升级到版本 `2` 的登记与执行链路。它不改变业务 Schema，也不需要数据回填或回滚。

后续迁移开始承担实际 Schema 变更；不得将变更追加回 `001_initial.sql`。

## 三、备份格式

### 3.1 文件位置与命名

- 存放目录：应用数据目录下的 `luluKing/backups/`。
- 文件名：`luluKing-backup-<UTC 时间>.json`。
- 创建时使用“仅新建”写入，避免覆盖同名备份。
- 最近备份由目录中最新且格式有效的 JSON 文件确定，不依赖 AI 设置或其他配置文件。

### 3.2 顶层结构

```json
{
  "format": "luluKing-backup",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "databaseVersion": 4,
  "exportedAt": "2026-08-13T00:00:00.000Z",
  "attachmentPolicy": "excluded",
  "data": {
    "tasks": []
  }
}
```

字段说明：

| 字段 | 含义 |
|---|---|
| `format` | 固定为 `luluKing-backup`，用于拒绝无关文件。 |
| `formatVersion` | 备份格式版本；导入时据此选择兼容逻辑。 |
| `appVersion` | 生成备份的应用版本。 |
| `databaseVersion` | 生成备份时的已注册迁移版本。 |
| `exportedAt` | UTC ISO-8601 导出时间。 |
| `attachmentPolicy` | 当前固定 `excluded`，明确附件内容不在备份中。 |
| `data` | 业务表快照，保留原始主键与关联字段。 |

### 3.3 导出表范围

| 范围 | 表 |
|---|---|
| 执行 | `tasks`、`checklist_items`、`events` |
| 组织与方向 | `goals`、`projects`、`materials` |
| 例行 | `habits`、`habit_logs` |
| 知识 | `subjects`、`notes`、`note_links` |
| 横切与规划 | `tags`、`taggables`、`reviews`、`plans` |
| 排除 | `files`、附件实际文件、`sync_state`、AI 设置、日志 |

软删除记录会一并导出，以保留将来的同步和恢复语义。导出时按稳定主键顺序读取；`taggables` 按其复合主键顺序读取。

### 3.4 后续导入顺序

恢复尚未实现，但未来导入必须先完成完整校验，再按下列顺序在单个事务中写入：

1. `goals`、`subjects`、`tags`
2. `projects`、`habits`、`notes`、`reviews`、`plans`
3. `tasks`
4. `materials`、`checklist_items`、`events`、`habit_logs`、`note_links`、`taggables`

导入前至少校验格式、版本、日期、数组类型、主键唯一性、枚举值以及外键引用。校验或写入任一环节失败时，必须不改变现有业务数据。

## 四、实现与错误策略

### 4.1 导出流程

1. 创建备份目录。
2. 读取所有纳入范围的业务表。
3. 写入版本、时间、附件策略和数据快照。
4. 使用只新建模式写入 JSON 文件。
5. 返回文件名、时间和各表记录数，供设置页展示。

数据库读取或文件写入失败时，不返回“成功”，也不更新最近备份显示。备份不会读取或写入 AI 配置，因此不会包含 API Key。

### 4.2 一致性限制

第一版导出在前端按只读查询生成快照。当前应用是单窗口本地应用，导出期间不会主动修改数据；在恢复功能上线前，完整原子恢复会下沉到 Rust 端实现。

若后续出现后台写入、多个窗口或大数据量场景，导出也应迁移到 Rust 端，使用 SQLite 只读事务或数据库原生备份 API 生成一致快照。

### 4.3 测试要求

- 验证每张业务表都会被读取，且 `files`、`sync_state` 不会导出。
- 验证格式解析会拒绝损坏 JSON、错误标识、未来格式版本和缺失表数据。
- 验证目录创建、文件命名和只新建写入选项。
- 验证最近备份查询能返回有效文件，并对损坏的最新文件报错。
